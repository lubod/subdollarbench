### F6. The connection-cap check doesn't race the closes before it

- CI run `42655763250` (on `d8b0281`, a docs-only commit; the same code
  passed before and after) failed
  `verifier::sql::security::tests::a_faithful_server_passes_the_whole_scenario`:
  "connection 3 of the first 4 was refused: ... too many connections".
- The cause is in the verifier, not only the mock:
  `connection_cap_check` (`src/verifier/sql/security.rs:345`) fills the
  cap right after the earlier checks dropped their connections
  (`statement_timeout_check`, `slow_loris_check`). A correct server that
  frees a slot when it notices the close can still count a closed socket
  for a few milliseconds and refuse one, and the candidate fails stage 18
  although it's correct. The release step at the end of the same check
  already retries (`src/verifier/sql/security.rs:382`); the initial fill
  doesn't.
- No run so far has hit it: no published or hidden `live.log` contains
  "of the first ... was refused".
- **Fix:** during the initial fill, a refusal answered `ERR limit` (too
  many connections) is retried for up to 2 s (50 ms apart), like the
  release step. Any other refusal, or a cap still full after 2 s, fails
  as today. The check's other verdicts don't change.

Acceptance:
- [ ] A test with a mock server that frees a slot 20-100 ms after a close
  (a faithful but slow-to-release server) passes with the fix and is seen
  failing without it.
- [ ] `a_faithful_server_passes_the_whole_scenario` passes 50 times in a
  row (`--test-threads` as CI runs it); the command and count in the
  notes.
- [ ] A server that never releases still fails with the existing
  message.

## Spec questions

**F4, the 10 model checks.** Six pass (xiaomi/mimo-v2.6-flash,
openai/gpt-6-luna, qwen/qwen3.8-flash, z-ai/glm-5.3-flash,
inclusionai/ling-3.1-flash, tencent/hy4). Four fail; the item says any
FAIL stops the round with a spec question:

1. **deepseek:** sent exactly
   `deepseek/deepseek-v4.1-flash-1017`, OpenRouter served
   `deepseek/deepseek-v4.1-flash-20261017` (the dated permaslug; `-1017`
   is 10/17). The check's served-prefix rule fails. Is this the same
   model, and should the check accept the served base before the trailing
   version, or is the row wrong?
2. **anthropic 2.08× and openai/gpt-6-luna-pro 2.37× the snapshot.** The
   pinned `openai` provider has three live tiers (0.05/0.25, 0.1/0.5,
   0.2/1.0); luna passes on 0.1/0.5 and luna-pro fails at 2.37×, so its
   pin may route to 0.2/1.0. The anthropic row is 0.1/0.5; its cache
   write (0.125) explains 2.08×, and the check's expected uses only
   prompt+completion, not the cache write/read. Should the rows use the
   live tier (noting both) and/or the bill check use the cache rates?
3. **minimax:** the generation API returned "not found" after the 20 s
   retry; the omp call and the tool round trip passed. Rerun.

- **Answer (reviewer, 2026-11-09 17:56 CET / 16:56 UTC).**
  1. **deepseek: the same model; fix the check, not the row.** OpenRouter's
     model record carries `canonical_slug`
     (`/api/v1/models`): `deepseek/deepseek-v4.1-flash-1017` →
     `deepseek/deepseek-v4.1-flash-20261017`, exactly what was served.
     The check compares the served id with the model's
     `canonical_slug`, exactly (not a prefix). That is also stricter:
     a prefix would let `tencent/hy4` match `tencent/hy4-preview-...`.
  2. **The bill: compute the expected cost the way the harness does.**
     Use the generation record's own token counts (prompt, cached,
     completion, and cache writes where reported) with **all four**
     snapshot rates, the same formula as `src/cost/calculator.rs`; then
     compare. Rerun anthropic and luna-pro with that.
     - If **luna-pro is still over 1.25×**, the `@openai` pin is likely
       reaching the `openai/fast` tier (0.2/1.0, 2×). Then find out
       from the generation record (cost per token against the three
       tiers) which tier served it, and stop with a spec question; the
       pin may need the exact tier. The rows stay on the snapshot
       prices until then.
  3. **minimax: rerun** (the generation API's eventual consistency).
     If it still can't find the record after 60 s, record that and
     retry once more later.
