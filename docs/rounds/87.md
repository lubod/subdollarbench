## Items

### F1. The billing path streams the response through

The `/api/v1` billing path forwards the upstream's status line and
headers as soon as they arrive, then each body chunk as it arrives
(chunked or SSE), never buffering the whole response. It keeps a copy
(or the tail that holds the final `usage` chunk) and appends the same
`billing_record` (`extensions/egress_proxy.py:31`) when the upstream
ends. A non-streamed JSON answer still works. A client that hangs up
mid-stream still produces a billing record for what the upstream sent.
The upstream read time-out stays a per-read guard (180 s), not a whole-
response limit.

Acceptance:
- [x] A stub upstream that sends headers at once and then SSE chunks
      over a period longer than the client's header wait: the client
      receives the headers and the first chunk before the upstream
      finishes, and `billed.jsonl` gets one record with the final
      chunk's `id` and `usage.cost` — test:
      `r87_f1_billing_proxy_streams`
- [x] A plain JSON (non-stream) answer is forwarded whole and billed as
      before — test: `r87_f1_billing_proxy_plain_json`
- [x] A client that disconnects mid-stream: the proxy doesn't crash,
      serves the next request, and bills the first — test:
      `r87_f1_client_hangup_still_billed`
- [x] `r85_f1_billed_from_the_calls` and `r85_f1_cell_isolation` still
      pass
- [x] Each new test seen failing against the buffering proxy

### F2. A turn interval never wraps backwards to a day

`src/campaign/health.rs:154`, `:263` and `:274` take a turn's duration
as `(end + 86_400 - start) % 86_400`, so an end stamp a few seconds
before its start (a resume's lines) reads as 86,394 s, the
`turn_secs_max` both stopped runs show. Wrap only for a real midnight
crossing (the end is more than 12 hours "before" the start); any other
backwards step is 0 s.

Acceptance:
- [x] 23:59:50 → 00:00:10 is 20 s; 02:51:51 → 02:51:45 is 0 s; the
      grid's `p50 > 180` warning isn't raised by such a step — test:
      `r87_f2_no_backwards_day`
- [x] Seen failing

### F1 (done)

`extensions/egress_proxy.py`: `handle_billing` keeps `resp_body`
(`:107`); `send_client` (`:114`) swallows a client write error
(`client_ok = false`), so a hangup stops the client writes, not the
upstream read; the status line and headers are sent at once
(`:135-140`), then each `resp.read1(65536)` chunk is forwarded (`:147`);
`billing_record(bytes(resp_body), …)` runs when the upstream ends
