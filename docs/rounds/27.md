## Why

The freeze makes a published score comparable across cells. Three review
findings mean it isn't comparable yet, and one check from the proposal
was never run:

- **R24-4** (`24.md`, Review): the rules stamp isn't stable.
  `fingerprint_files` (`src/report/rules.rs:841`) and `fingerprint_root`
  (`:857`) use `DefaultHasher`, whose algorithm Rust may change between
  releases, and keep 32 bits. They also read the graded files from disk,
  but the verifier, the pipeline, the prompts and the price snapshot are
  compiled into the binary. A binary built from an older tree can report
  the new tree's stamp.
- **R24-6** (`24.md`, Re-review): two snapshot ids in
  `src/cost/model_prices.json` aren't in the catalog,
  `anthropic/claude-3-haiku` and `meta/muse-spark`. Since round 24 the ids
  match exactly, so these entries never match anything.
- **R26-2** (`26.md`, calibration on `.40`): the list price and the bill
  differ. Over the P1 cell the bill was $0.514 against $0.424 at list
  price (+21 %); per ticket, from −34 % to +84 %. The token accounting is
  not the cause (OMP counts reasoning in `output`).
- **Flake bar** (`docs/PROPOSAL-sdb-sql.md:430`): "each stage passes
  20/20 against the reference adapter." It was never run as a bar. Three
  stages have no live proof at all: 12, 12 lite and 15 lite
  (`src/pipeline.rs` has 22 `test_pipeline_eval_only_sql_stage*_live`
  tests; none of them covers these three).

CI and the final rules version are the freeze itself; they go to round
28 (see "Out of scope").

### F5. A resumable flake-bar script

- `scripts/flake-bar.sh [--passes K] [--only <test>]` runs K more passes
  (default 1) over every `test_pipeline_eval_only_sql_stage*_live` test,
  one test at a time, niced. It reads the list from `src/pipeline.rs`, as
  `gate.sh --fast` does. `--only` limits it to one proof, for the rerun
  after a fix.
- **Resumable:** results accumulate in one record per commit,
  `<git-common-dir>/sdb-gates/<commit>.flake.txt`. Each finished test run
  appends one line (test, pass/fail, seconds, UTC time) as soon as it
  ends, so a chunk stopped part-way (Ctrl-C, or a reboot) keeps what it
  finished, and the next call carries on.
- The record ends with a summary over every line so far: per proof
  `passes/runs`, then one of:
  - `RESULT: PASS` when every proof has at least 20 runs and no failure;
  - `RESULT: IN PROGRESS (min runs k/20)` while any proof has fewer than
    20 runs and none has failed;
  - `RESULT: FAIL` as soon as any run has failed, naming the proofs.
- A failing run keeps its test output tail in the record, as `gate.sh`
  does, so the finding can cite it.

Acceptance:
- [x] Three passes on the ready commit, run as two chunks (1, then 2) so
  the resume path is used — evidence: the record path, its summary and
  RESULT, under Implementer notes.
- [x] The summary logic (PASS / IN PROGRESS / FAIL, a partly finished
  chunk, `--only`) is tested on a fixture record without Docker — test:
  `scripts/flake-bar.sh --self-test`.
- [x] The script refuses a dirty tree, as `gate.sh` does.

**Findings:**

- **R27-1 (blocker): two runtime inputs are hashed at build time.**
  - `graded-files.txt` lists `file campaigns/sdb-sql/campaign.json` and
    `dir tasks`. Both are read from disk at run time:
    - `load_campaign_from` reads `campaign.json` (`src/campaign.rs`
      ~:513), and it holds the ladder and the lite profiles;
    - the task prompts are read as `…/prompt.md` (`src/config.rs`
      ~:1479).
  - So editing `campaign.json` under `SDB_HOME` changes grading without
    moving the stamp until the next rebuild. Round 24 hashed it from
    disk, so this is a regression.
  - Fix: make both runtime entries (a `runtime-file` kind, or
    `runtime-dir campaigns/sdb-sql` in place of the stages entry). Test:
    editing `campaign.json` under a temp `SDB_HOME` moves
    `fingerprint_root`.
- **R27-2 (blocker): the OMP bench policy isn't in the stamp.**
  - `extensions/bench-policy.js` is compiled in (`src/sandbox/omp.rs`
    ~:122) and runs inside the candidate's session: it blocks forbidden
    tools and steers the wrap-up near the turn limit. That's
    candidate-visible, and F1 asks to hash what the binary grades with.
    It was never in the stamp (round 24 missed it too).
  - Fix: `file extensions/bench-policy.js`. Widen
    `r27_f1_every_graded_source_is_listed` so every `include_str!`
    target under `src/pipeline.rs`, `src/sandbox`, `src/cost` and
    `src/prompts` must be listed.
- **R27-3 (blocker): the flake record is keyed by commit, so it can't
  resume across commits.**
  - `scripts/flake-bar.sh` writes `<commit>.flake.txt`. The 20 passes
    run on master over several nights (D2), and master gets a new commit
    for every merge and round-file change. Each one would start an empty
    record, and the chunks would never add up to 20.
  - Fix: key the record by the graded content, not the commit. For
    example, hash `git ls-tree -r HEAD` over the gate's `GRADED_PATHS`,
    `extensions/` and `scripts/flake-bar.sh`, and name the record
    `flake-<hash12>.txt`. Each `started:`/`resumed:` line names the
    commit it ran on. A commit that only touches docs keeps the key.
  - The `--self-test` should cover it: two commits that differ only in
    a doc file give the same record path.
- **R27-4 (next → round 28): flake-bar ergonomics.**
  - The first failure stops the whole chunk (`break 2`), so a night with
    one flake gathers nothing on the remaining proofs. Finishing the
    pass would give more evidence for the same night.
  - With `--only`, the summary covers that one proof and can print
    `RESULT: PASS` for it alone. The summary should always cover all
    proofs.
- **R27-5 (next → round 28):** `r27_f1_compiled_in_files_hash_the_build`

  that recomputes the compiled digest from the source tree and compares
  it with `COMPILED_GRADED_DIGEST` would.
- **R27-6 (next → round 28):** F2 changed three Gemini cache-write

- **R27-7 (next → round 28):** `CAP_PRICE_BASIS` isn't shown anywhere
  yet (no caller outside the tests). The freeze should show it where
  results are read, on the Board's rules view or in the portal export.
