## Why

Two findings from round 29 (`29.md`, Review), both outside the graded
paths:

- **R29-2: CI runs the fast test set twice.**
  - `.github/workflows/ci.yml` runs `bash scripts/gate.sh --fast`, which
    runs `fmt`, `clippy` and `cargo test` with the `SQL_PERF_LIVE` skips
    (`scripts/gate.sh:86-97`).
  - It then runs `cargo llvm-cov` over the same set. The same steps also
    run `cargo check`, `fmt` and `clippy` a second time, outside the gate.
  - So the run takes twice as long and the flake exposure doubles.
    Instrumentation also slows timing-sensitive tests: the implementer
    saw `stage6_transactions_live` slow down under it, and the pubsub
    mock p99 flake (`29.md`, Implementer notes).
  - The skip list is written twice, as the same `awk` over
    `src/pipeline.rs` in `gate.sh:91-95` and in `ci.yml`.
  - That list holds the 14 proofs that take the `SQL_PERF_LIVE` lock,
    plus `test_tests_gate_sensitivity_end_to_end`: 15 names. The other
    11 live ladder proofs (`stages_0_3`, stages 4-10, and the 5, 8 and 11
    lite ones) take no lock (for example
    `test_pipeline_eval_only_sql_stage6_transactions_live`,
    `src/pipeline.rs`). So the fast gate and CI run them, in parallel
    with the rest. They are part of the measured 84.63 %.
- **R29-4: the Board's rules fallback reads a field that does not exist.**
  - `loadRulesVersion` (`src/web/index.html:2986-2993`) falls back to
    `(await fetch('/api/status')).json().rules_version`.
  - `StatusResponse` (`src/web/server.rs:149`) has `sqlite_version`
    and `cap_price_basis`, but no `rules_version`.
  - The page injection (`serve_index`, `server.rs:734`) covers the Board today, so
    the fallback is dead code.

**The flake bar is running.** The 20-pass flake bar on `5ebad6e` runs in
chunks until the freeze (`27.md`, "After the merge"). Its record key
hashes the paths in `scripts/graded-paths.txt`, so this round must not
touch any of them. Its gate must also not run while a chunk is running
(see "Gate" below).

**The first GitHub CI run (R29-1) failed at clippy**, on a newer
toolchain (`29.md`, "R29-1"). F1 now pins the toolchain too. Tests have
not run on the runner yet, so the next GitHub run may show more.

**Open question for the operator (decide before open):** should CI also
skip the 11 lock-free live proofs? They need Docker on the runner, and
they run under instrumentation, where the implementer saw
`stage6_transactions_live` slow down. The full gate and the flake bar run
them anyway. Skipping them would lower coverage below the 84 % ratchet,
which was measured with them in. Reviewer's recommendation: keep them
unless the first GitHub run shows they fail or flake there.

## Items

### F1. CI runs the fast set once, from one skip list (R29-2)

- **Pin the toolchain (R29-1).** The first GitHub run failed at clippy:
  `@stable` gave Rust 1.99, and its clippy raises 6 lints that 1.92.0
  doesn't, all in `src/verifier/sql/` (`29.md`, "R29-1"). Pin CI to the
  bench's toolchain, 1.92.0, either in `ci.yml` or in a
  `rust-toolchain.toml` that both read. Don't fix the lints here:
  `src/verifier` is a graded path, so fixing them would move the flake
  record. A toolchain bump, with its lint fixes, is a later round of its
  own.

- Drop the `gate.sh --fast` step from `ci.yml`. The `llvm-cov` step stays
  and is the only test run, keeping `--fail-under-lines 84`.
- Keep one `fmt` step and one `clippy` step. `cargo check --all-targets`
  is covered by `clippy --all-targets`, so drop it.
- One skip list. A small script (for example `scripts/live-proofs.sh`)
  prints the `SQL_PERF_LIVE` proof names, one per line. `gate.sh --fast`
  and `ci.yml` both read it. Don't put the script under any graded path.
- `gate.sh` itself is unchanged apart from reading the shared list. It
  stays the round gate.
