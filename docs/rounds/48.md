# Round 48: careers in parallel lanes

Status: draft
Opened: —
Branch: `round48`
Rules: `2026-10-19.42` (unchanged: what is graded and what the candidate
sees stay the same; the pipeline is a graded path, so the full gate and
a new 20-pass bar apply)

## Why

The grid runs one cell at a time. Measured on the stopped `.42` grid,
a career takes about 5.5 h (deepseek 22:15Z-03:33Z, Haiku 04:14Z-09:03Z,
2026-10-27/28), so 15 careers take about 82 h. The host has 24 cores and
53 GB; a candidate container is capped at 2 CPUs
(`src/sandbox/docker.rs:287`), and the API side doesn't limit
parallelism (each model has its own provider). Operator, 2026-10-29:
"tell me how to parallelize careers", then "ok plan it".

Three things stop two cells from running side by side today:

- **One worker slot.** `campaign run` hard-codes `worker: 0`
  (`src/main_campaign.rs:1057`), so every cell binds the worker-0 ports.
  `scripts/sql-cell.sh:80` refuses a second cell because port 5480 is
  taken. The pipeline already offsets ports by worker
  (`crate::web::server::worker_port`, `src/web/server.rs:101`; for
  example the reference SQL at `src/pipeline.rs:4933`); only the CLI
  doesn't pass one.
- **No lock between cells.** `SQL_PERF_LIVE` is a test-only mutex
  (`src/pipeline.rs:10652`, inside `mod tests`), so it serializes the
  live proofs inside one `cargo test` process and nothing in a real
  cell. Ticket 11's gate has absolute limits (5 ms medians,
  `src/verifier/sql/perf.rs:40-44`), and crash recovery, concurrency,
  disk-full and replication all time their checks. A neighbour's
  grading or build could fail a ticket that passes alone.
- **The grid driver is serial and lives outside the repo** (the
  reviewer's scratchpad).

This round is for the v2 grid (round 45, rules `.43`). The `.42` grid
running now stays serial, so all its careers are measured under the
same conditions as the calibration.

## Decisions (operator, before open)

- **D1, how many lanes:** (a) 3, one per career round (about 28 h for
  15 careers; recommended: no more than 3 graders wait on the lock); (b)
  5, one per model (about 17 h); (c) set per grid, default 3.
- **D2, lock wait and the wall cap:** (a) time waiting for the grading
  lock (F2) is recorded and does not count toward the 8 h wall cap
  (recommended: a cell must not lose wall time to its neighbours); (b)
  it counts.

## Items

### F1. `campaign run --worker N`

- A `--worker <0-7>` flag (default 0) on `campaign run`, passed into
  the pipeline config in place of the literal at
  `src/main_campaign.rs:1057`. Every port the cell binds comes from
  `worker_port(base, worker)`.
- `scripts/sql-cell.sh` takes `SDB_CELL_WORKER` (default 0), passes
  `--worker`, and checks that worker's candidate port instead of 5480
  (`scripts/sql-cell.sh:80`).
- The "unreachable" message at `src/campaign.rs:3619` names the
  worker's port, not 5480.
- The workspace, the run id, container names and networks are already
  per run; the implementer confirms none is per worker-0 only, or fixes
  it here.

Acceptance:
- [ ] The flag reaches the pipeline config, and worker 3's candidate,
  reference and pool ports are base + 300 — test:
  `r48_f1_worker_flag_sets_ports`.
- [ ] Two cells on workers 1 and 2 share no host port — test:
  `r48_f1_two_workers_share_no_port` (extends round 37's port table,
  `r37_f1_worker_ports_do_not_collide`).
- [ ] `CELL_DRY_RUN=1 SDB_CELL_WORKER=2 scripts/sql-cell.sh <model>`
  prints `--worker 2` and checks worker 2's port — check: the command
  and its output in the notes.

### F2. A host-wide grading lock

- The verification step of a ticket (the `TaskType::Sql` arm at
  `src/pipeline.rs:3166`, from starting the candidate to the verdict,
  including shrink) takes an exclusive `flock` on
  `<SDB_HOME>/runs/.grading.lock`. The model's session, builds and the
  harness's other work stay parallel.
- The phase rollup records, per stage, the seconds spent waiting for
  the lock (`grading_wait_s`). With D2 (a), that wait is excluded from
  the wall-cap check.
- The lock is released on every exit path (a panic, a timeout, a
  harness fault); a lock file left by a killed process doesn't block
  (`flock` is released with the descriptor).

Acceptance:
- [ ] Two processes grading at once run one after the other: the
  second's grading starts after the first's ends — test:
  `r48_f2_grading_is_exclusive` (two child processes, timestamps).
- [ ] The wait is recorded in the rollup and (D2 a) not charged to the
  wall cap — test: `r48_f2_wait_is_recorded_not_charged`.
- [ ] A process killed while holding the lock doesn't block the next
  one — test: `r48_f2_killed_holder_releases`.

### F3. Proof under load

The evidence that a ticket graded next to running cells gets the same
verdict as alone.

- `scripts/flake-bar.sh --load <L>` runs the usual live proofs one at a
  time and, for the whole run, `L` load containers in the sandbox
  image, each capped like a candidate (`--cpus=2`), each doing what a
  model's session does: a compile loop and a write-and-`fsync` loop.
  They carry a label, and the script removes them on every exit.
- The record key gains the load (`flake-<key>-load<L>.txt`), so it never
  stands in for the plain bar.

Acceptance:
- [ ] `--self-test` covers the load option: containers started,
  labelled, removed on exit and on Ctrl-C — test: the self-test.
- [ ] **After the merge (reviewer):** 5 passes with `--load` set to D1's
  lane count minus one, 0 failures; ticket 11's index/scan ratios are
  within 20 % of the plain bar's — check: the record, in this file.

### F4. `scripts/grid.sh`: the grid driver, with lanes

- The reviewer's driver moves into the repo (from the scratchpad
  `grid-driver2.sh`): a preflight before every phase (a clean tracked
  tree, the bar record for the graded key, nothing else on the lane's
  worker), the post-phase checks (phase, harness fault, over budget,
  over wall, cost over $0.99, an `infra_error`, a wall stop), the hold
  file, resume, and a ledger.
- `--lanes N` runs N careers at once, lane `i` on worker `i + 1`. A
  lane runs its careers' phases 1-4 in order (phases chain). All lanes
  share one ledger and one spend cap; a STOP on any lane stops new
  phases on every lane and lets running ones finish.
- The hold (`gap`) applies to every lane at its next phase boundary.

Acceptance:
- [ ] With a fake cell script (`SDB_GRID_CELL=<fake>`), 3 lanes run 6
  careers: each career's phases run in order and chain, no two lanes
  share a worker, and the ledger has 24 rows — test:
  `scripts/grid.sh --self-test`.
- [ ] A STOP on one lane starts no new phase on any lane; the cap counts
  all lanes — test: the self-test.

### F5. Each cell says how it ran

- `campaign.json` records the worker and how many cells ran at once
  during the phase (`concurrent_cells`, read from the lock directory or
  the driver), and the summed `grading_wait_s`.
- The run page shows them in the cell's details. The board and the
  score don't change.

Acceptance:
- [ ] A phase rollup carries `worker`, `concurrent_cells` and
  `grading_wait_s` — test: `r48_f5_rollup_says_how_it_ran`.

## Out of scope

- **Running the `.42` grid in parallel:** it stays serial (see "Why").
- **More than one cell per worker, or cells from the engine's queue:**
  lanes run CLI cells only.
- **Round 45's perf run:** it measures under the bench lock. With this
  round merged first, that lock is F2's `flock` (a production lock), not
  the test-only `SQL_PERF_LIVE`; round 45's implementer asks under its
  Spec questions when it starts.
