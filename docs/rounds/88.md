## Spec questions

1. F1's fresh target alone did not fix the `.48` failure. `llvm-cov
   export` with every test binary as a positional argument reads only
   the first one's files, so "no source lines under src/" meant "the
   first test binary cargo reported was `tests/pg.rs`". The fresh target
   happened to put the suite first in the reviewer's reproduction, but
   the order is not deterministic (my fixtures saw both). The fix passes
   every binary to one export with `--object`, which merges their
   coverage (a file tested by two binaries is counted once, with the
   union of its lines). The spec says "the rest of the measurement is
   unchanged"; this is a change to the export call, needed for the
   acceptance's "measures the true coverage". Is that acceptable as
   part of F1?

   **Reviewer (operator: "approve"):** yes, part of F1, and now its
   core: the reviewer's reproduction misread the cause (only the first
   binary's files were read). Passing every test binary with `--object`
   stays; the fresh target stays as the guard against a stale or planted
   `target/`. See **Changes after open** for the added test.

2. F1's stale-target test makes the plain build's `target/` read-only,
   so the old measurement (which reads the workspace target) fails to
   write its lock; the fresh build ignores it and reads the true
   coverage. The acceptance offers "a fixture that builds, edits a
   source file with an older mtime, and measures"; on the sandbox's
   cargo 1.100 that fixture rebuilt the edited source (the reading was
   the true one), because the build-dir freshness is content-based. The
   read-only target is the deterministic form of "a stale or planted
   target cannot change the reading". Is that the intended guard?

   **Reviewer:** yes. The read-only `target/` is the intended,
   deterministic guard.

3. F1's planted-target test plants a prebuilt instrumented suite binary
   built from a source whose `tested` calls `untested` (2/3 coverage)
   over the real source's binary (1/3); a measurement that reads the
   workspace target reports the planted 66.67 %, the fresh build 33.33 %.
   On the reverted code the record's failure is at the measurement (the
   `pg` binary is first, so "no source lines") rather than the value
   assertion; the fixture keeps the `pg` test (the haiku shape). Is the
   planted-binary mechanism the intended guard?

   **Reviewer:** yes, the planted-binary mechanism is the intended guard.
