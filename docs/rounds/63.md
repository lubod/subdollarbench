## Why

- **R61-12: a port race floors a candidate's perf score.** The bar on
  `539a58e0c8c8` passed with one cured failure (`61.md`, "After the
  merge"). `r45_f5_perfscore_cli` failed in 1 s on `candidate sandbox
  failed to start: docker: ... Bind for 127.0.0.1:42281 failed: port is
  already allocated`, and every workload was floored at 0.100 with
  `correct NO`.
  - `run_workspace_at` takes both ports from `free_port()`, which binds
    `127.0.0.1:0` and drops the listener at once
    (`src/verifier/sql/perfscore.rs:1450-1453`, called at `:1576-1577`).
    The two calls can return the same port, and another process can take
    either port before `docker run` binds it.
  - A candidate container that fails to start returns
    `PerfScore::floored` (`:1590-1599`): the candidate's 0.1, not
    `PerfScore::harness_fault` (`:120`, which leaves the block without a
    score).
  - The same code scores every graded phase's perf block, so it reaches
    published v2 results. On the bar, 1 of 40 `run_workspace_at` runs
    hit it.
  - No other production code picks a port this way. The
    `src/sandbox/docker.rs:2320` one is test-only and already removes
    duplicates.
- **R61-8: the faster bar** (`61.md`, F8's table and proposals). One bar
  pass takes about 52 min, and 20 passes about 17.5 h. Most of that time
  repeats work:
  - every stage proof from 14 on regrades the differential stages 0-13
    (64.4-64.6 s each);
  - stages 17-20 repeat every earlier late check (about 366 s per pass);
  - `r45_f1` is 360 s per run, 304 s of it W5.
- **Operator, 2026-11-03 ("1a no bump"):** fix R61-12 before any grid
  cell, together with R61-8, since both move the key anyway. One bar
  then covers both, and the grid starts after it. No rules bump.

## Items

### F1. Perf ports are held until bound, distinct, and a host-side start failure isn't the candidate's (R61-12)

- `run_workspace_at` reserves both ports with listeners it keeps. They
  must differ: re-pick until they do. Each listener is dropped just
  before its own container's `docker run`.
- **The candidate's container start:** when it fails with a Docker
  daemon error that comes from the host (`port is already allocated`,
  `address already in use`, or `Error response from daemon` before the
  container runs), it retries once on a freshly reserved port. If that
  fails too, the result is `PerfScore::harness_fault`, not `floored`.
- **The candidate's own failures still floor**, as today: the build,
  `start.sh` exiting, not answering within 30 s, or a wrong answer.
- **The reference side is unchanged.** It already returns an error that
  the caller treats as a harness fault.
- The doc comments on `floored` and `harness_fault` (`:107-120`) say
  which start failures belong to which.

Acceptance:
- [ ] Two reservations never return the same port, even when the OS
  hands back the same one. Test: `r63_f1_ports_distinct`, with a port
  source stubbed to return 5000 twice and then 5001.
- [ ] A start error containing `port is already allocated` retries once
  and then gives `harness_fault` (the block has no score). A `start.sh`
  failure still gives `floored`. Test: `r63_f1_host_start_failure_is_harness`,
  with the start step stubbed.
- [ ] Seen failing: with the classification removed (every start error
  floors), `r63_f1_host_start_failure_is_harness` fails.
- [ ] `r45_f1_reference_scores_one` and `r45_f5_perfscore_cli` still
  pass (the `--ready` gate picks them through `scripts/proof-map.txt`).

  under 0.5 s and may stay.

  - or through a test-only knob.

  Ask under **Spec questions** first if the pipeline needs a production
  change for this. A production change is out of scope without a new
  decision.

Acceptance:

### F3. Late-check proofs stop repeating earlier late checks (R61-8, proposal 2)

- The stage-20 proofs keep every late check.
- If the late checks are chained in production code and can't be
  separated from a test, ask under **Spec questions** before changing

Acceptance:

### F4. `r45_f1` runs 5 times per bar, not 20 (R61-8, proposal 3)

- The bar list gives each proof a run target: 20 by default, and 5 for
  `r45_f1_reference_scores_one`. Put the target next to the name in
  `scripts/bar-proofs.sh`, or in a data file it reads.
- Five runs keep its production-shaped self-check in every bar, and save
  15 × 6 min. The test itself keeps `PerfConfig::default()`.
- `summary` and `run_chunk` (`scripts/flake-bar.sh`) use each proof's
  target for "full", for skipping, and for `min runs`.
- The cure limits are unchanged: one per proof, two per bar.

Acceptance:
- [ ] Self-test fixtures:
  - a 5-run proof at 5/5 next to 20-run proofs at 20/20 gives

  - at 4/5 it gives `IN PROGRESS`;
