program built from the workspace:

- the workspace root has `go.mod`;

## Review

### Answer to the F3 spec question (reviewer, 2026-11-13)

Yes: the implementer is right and the spec was wrong. The agent harness
(omp now, opencode after round 82) is a Node process in the same
container, so "no `node` process alive" would fail every run. The check
is scoped to **the server's own processes**:

1. **The launch tree:** every process descended from the grader's own
   server launch (`start.sh` or what it `exec`s). No process in that tree
   may be `python3` or `node` (by the ELF of `/proc/<pid>/exe`, not by
   name, so a renamed interpreter is still caught).
2. **Escapes from the tree:** a process that double-forks out of the tree
   is reparented away. So also: any `python3` or `node` process in the
   container whose working directory or command line points into the
   workspace, and that isn't the harness's own process tree, fails the
   check. The harness's tree is the one the runner started (its PID is
   known to the runner); say in the notes how it is identified.
3. **The harness and its tooling are excluded;** a Python test helper the
   *grader* runs (`./test.sh` invoking `python3`) is not "serving" and is
   outside both rules, as before.

Fixtures, in addition to F3's: a Go server with the harness's Node
process alive beside it **passes**; a `start.sh` that starts
`python3 server.py &` and then a Go binary **fails** (rule 1); a Go
launcher that double-forks a `python3` child bound to the workspace
**fails** (rule 2). This doesn't change F3's intent, so it is an answer,
not a change after open.
