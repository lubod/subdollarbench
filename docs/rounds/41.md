## Why

The operator wants only the sdb-sql campaign (2026-10-27, "plan a a"):

- **D1 = (a):** delete the retired tasks before calibration, so every
  published cell runs on the final code with one fingerprint. The 20-pass
  bar on the old content was stopped (`37.md`, "After the merge").
- **D2 = (a):** old sdb-sql rows stay readable. The archived cells in
  `/home/ubuntu/sdb-archive/2026-10-27/` must render if moved back.
  Rows of the retired tasks need not.

The deletion is two rounds:

- **This round** removes the callers (CLI commands, API routes, the
  console's legacy controls, the per-run portal). It touches no graded
  path and no file the fingerprint hashes, so it needs only the fast
  gate.
- **Round 43** then deletes the retired verifiers, tasks and pipeline
  paths, which are graded.

What only the retired benchmark uses today (round 40's analysis, "Why"):

- **CLI** (`src/config.rs:87-1117`):
  - single runs with trials and pass@k: `run`, `eval`, `enqueue`,
    `extend`, `queue-extend`, `stability`;
  - per-task boards: `leaderboard`, `lboard`, `matrix`,
    `matrix-report`;
  - the review judge: `review-run`, `regen-reviews`, `review`;
  - repairs of old single-run rows: `backfill`, `repair`,
    `cost-annotate`, `annotate-cutoff`, `migrate`;
  - re-verifying single runs: `replay`, `sdiff`, `ps`.
- **API** (`src/web/routes.rs:25-78`):
  - `/api/leaderboard`, `/api/compare`;
  - `/api/run` (a single run);
  - `POST /api/queue` (enqueue a single run);
  - `/api/runs/:id/extend`, `/api/runs/:id/review`.
- **Console:** Admin's "Legacy (not campaigns)" controls (single run,
  Run Queue, review-judge model; `gui-spec.md` §4.4).
- **Portal:** per-run pages and the model-rollup portal, next to the
  sdb-sql board (`PortalExporter::export_sql_board`).

Round 40 (open) edits `eval`, `replay`, `run` and `enqueue` (F4, F5),
and this round deletes them. The operator kept round 40 as is (D3), so
that work is knowingly short-lived. Round 41 starts from master after 40
merges.

### F5. Cap the WAL retry time (R38-1)

`enable_wal` (`src/report/store.rs:42-53`) retries a busy WAL switch up
to 50 times. Each attempt can wait out the 5 s `busy_timeout` first, so
a `bench.db` held locked by another process can hold up the boot for
about 4 min before the fallback (`38.md`, "Review").

- Bound the whole retry by a deadline (for example 10 s), then fail as
  today.

Acceptance:
- [ ] With the file held locked by a second connection's open write
  transaction, `Store::open` returns `Err` within the deadline plus one
  attempt — test: `r41_f5_wal_retry_is_bounded`.
- [ ] `r38_f1_concurrent_fresh_open` still passes — check: the gate
  record.
