## Items

### F1. The perf workloads

A new `src/verifier/sql/perfscore.rs`, built on the ticket 11 gate's
method (`src/verifier/sql/perf.rs:1-20`): the candidate and the
reference run the same workload, alternating rounds, under the
`SQL_PERF_LIVE` bench lock, each in a container with the same CPU and
memory limits (`src/sandbox/docker.rs:120-123`, `:286`). Fixed seed and
sizes, published in the contract (F3):

| ID | Workload | Covers tickets | Metric |
|---|---|---|---|
| W1 | Point lookup by primary key, 1 client, 100k rows | 0-3 | p50 and p99 latency |
| W2 | Range + `ORDER BY ... LIMIT`, 1 client | 2, 11 | p50 latency |
| W3 | Two-table join + `GROUP BY`, 50k × 5k rows | 7-8 | p50 latency |
| W4 | Autocommit single-row `INSERT`, durable, 1 and 8 clients | 4-6 | commits per second |
| W5 | Mixed 80/20 read/write, 16 clients, 30 s | 6, 12 | throughput and p99 |

- A sample of each workload's answers is checked against the reference.
  A wrong answer scores that workload at the floor: a fast wrong server
  earns nothing.
- With D1 (b), phase 1 runs W1 and W4, phase 2 adds W3, phase 3 adds W2
  and W5, and phase 4 runs all five.

Acceptance:
- [ ] The reference against itself scores 1.0 ± 0.1 on every workload,
  over 5 repeats — test: `r45_f1_reference_scores_one` (live, under the
  bench lock).
- [ ] A candidate with a 2 ms sleep per statement scores below 0.5 on W1
  and W4 — test: `r45_f1_slow_candidate_scores_low`.
- [ ] A fast candidate with one wrong answer per workload scores the
  floor on it — test: `r45_f1_wrong_answer_is_floor`.

### F2. The score

- Per workload: `r = reference / candidate` (latency) or
  `candidate / reference` (throughput), clipped to [0.1, 100] (see
  the note below).
- The perf score is the geometric mean of the `r` values, so 1.0 = the
  reference, 2.0 = twice as fast, and no single workload dominates.
- Stored in the phase rollup as a `perf` block (each workload's raw
  numbers, `r`, and the score) and in the career rollup (`CareerRollup`,
  `src/campaign.rs:2358`).
- The perf run is harness time: it is never charged to the candidate's
  budget and does not count toward the wall cap.
- **Why the SQLite reference is the unit, not Postgres** (operator
  question, 2026-10-28):
  - The ranking doesn't depend on the unit. For two candidates, the
    ratio of their scores is the geometric mean of their own per-workload
    ratios; the reference cancels. The unit only sets what "1.0" reads
    as, and where the clip bites.
  - Answers are checked against the same oracle the ladder grades with
    (SQLite semantics, the dialect's error classes). Postgres differs in
    typing, NULL order and integer division, so its answers would need
    translation before they could be checked.
  - The reference already speaks the text protocol and runs in the same
    sandbox under the same limits (`src/verifier/sql/ref_server.rs:1-12`).
    Postgres would add a server image, its own tuning (`fsync`,
    `synchronous_commit` decide W4 outright) and a new flake surface to
    every bar.
  - Its weakness: "1.0" is Python plus SQLite, not SQLite alone, and
    SQLite has one writer, so W5 is an easy bar. The clip is therefore
    [0.1, 100], not [0.1, 10], so a fast engine isn't flattened on W5;
    F5's run on the `.42` servers checks that the clip doesn't bind.

Acceptance:
- [ ] Clipping and the geometric mean match hand-computed values —
  test: `r45_f2_score_math`.
- [ ] A phase rollup and its career rollup carry the `perf` block; the
  candidate's `total_cost_usd` is unchanged by the perf run — test:
  `r45_f2_rollup_carries_perf`.
