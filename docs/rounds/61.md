## Why

- **The 20-pass bar keeps restarting before it finishes.** The last bar
  that passed is `flake-9c90cfcf4b7b.txt` (2026-10-27, rules `.42`).
  Four bars have started since (`14a590f26873`, `4b04de447b27`,
  `4b11760f6ea4`, and the next one on round 60's key), and none has
  finished. So no official cell has run on v2 (`.43`-`.45`). The newest
  run directories are the 2026-10-31 smoke cells.
- **A test-only change moves the key.** Both hashes take whole files:
  - the flake key: `git ls-tree` over `scripts/graded-paths.txt`
    (`scripts/flake-bar.sh:16-21`);
  - the rules fingerprint: `digest_files` over
    `src/report/graded-files.txt` (`src/report/graded_hash.rs:93-109`,
    `build.rs:19-31`).

  About 25,000 lines of `#[cfg(test)]` code sit inside 36 graded files
  (for example `src/campaign.rs` from `:3886`, `src/pipeline.rs` from
  `:3986`). Round 59 changed only a test in
  `src/verifier/sql/concurrency.rs` and still restarted the bar, and so
  will any future fix to a unit test. Test code isn't in the release
  binary, so it can't change a grade.
- **One failure anywhere fails the whole bar.** The bar is 28 proofs ×
  20 runs = 560 runs, with zero failures allowed
  (`scripts/flake-bar.sh:88-122`). For it to pass with even odds, each
  run's flake rate has to be below about 1 in 800. Each flake found has
  cost a round and then a bar from zero, about 17 h each (`58.md`,
  `59.md`). Round 60 handles the problem for one proof; F4 handles it in
  the bar.
- **Long jobs die with the session that launched them.** On 2026-11-02
  the bar died at about 12:39Z when the opencode service restarted, and
  it left four containers behind (`59.md`, "After the merge"). Nothing in
  `scripts/` detaches: there is no `systemd-run`, `setsid` or `nohup`.
- **The full gate takes about 53 min, and the bar repeats it 20 times.**
  Round 59's full gate (`e29bf713f82c.txt`) spent 3,161 s in tests:
  - **lib, 2,783 s:** one serial run of the 28 live proofs under
    `SQL_PERF_LIVE` (`src/pipeline.rs:6506-6510`: they need an idle
    host). Each stage's proof regrades every earlier stage too
    (`accepted_stages: (0..=N)`, for example `:5533`), so stage 4 takes
    18 s and stage 20 takes 215 s (`flake-4b11760f6ea4.txt`, pass 1);
  - **bins, 361 s:** `r54_f1_rehearsal_cell_live` (`src/main.rs:1420`),
    which cargo runs only after the lib tests;
  - fmt and clippy, 25 s.

  Running the proofs in parallel is not an option: R59-1 shows that
  host load breaks the perf checks. But every proof runs 20 times in the
  bar after a merge, and no cell runs without a bar PASS. So the
  per-round gate only needs the proofs a round puts at risk.
- Source: the reviewer's process review (2026-11-02, recommendations 1,
  2 and 4); the operator asked for this draft ("draft 61"). The gate
  analysis (F6-F8) was added on the operator's "add it to current
  draft" (2026-11-02).
- **Size:** 9 items, over the usual 5, on the operator's word (F9 is
  round 60's one-line finding R60-1). Two
  themes that share one script set (`scripts/flake-bar.sh`,
  `scripts/gate.sh`, `scripts/graded-paths.txt`).

### F5. Long jobs outlive the agent session (D2 = a)

- `scripts/detach.sh <name> -- <command...>` launches the command so
  that a restart of the opencode or Claude service can't kill it. It uses
  `systemd-run --user --unit sdb-<name> --same-dir --collect` (D2 = a).
  It refuses, and says why, when linger is off for the user
  (`loginctl show-user "$USER" -p Linger`), because the job would then
  die at logout.
- It prints how to follow the job (`journalctl --user -u sdb-<name>
  -f`, or the log path) and how to stop it by PID or unit, never with
  `pkill -f`.
- It refuses when a job with the same name is already running.
- AGENTS.md (reviewer, at the merge): bars, grids, load bars and probes
  start through `scripts/detach.sh`.

Acceptance:
- [x] `scripts/detach.sh --self-test`:
  - a job launched from a subshell that then exits (and whose process
    group is killed) still writes its marker file;
  - a second launch with the same name is refused;
  - the job's exit status is readable afterwards;
  - with linger off (a stubbed `loginctl`), it refuses and names the
    fix.
