## Items

### R22-1. The crash label matches the real crash, not loose text

- `mark_agent_crash` (`src/campaign.rs` ~:1425) fires on `output: 65536`,
  `output limit` or `not valid JSON` anywhere in the console. Its message
  hard-codes "65,536".
- Failure: the agent crashes for another reason after an earlier tool-call
  validation error it recovered from. The stage is then mislabelled as an
  output-limit crash.
- Change:
  - Match the `[TOKENS]` line whose `output` equals that turn's maximum,
    followed by the provider `400` in the same session.
  - Put the real number in the line.

Acceptance:
- [ ] A console with a recovered JSON error and a later unrelated crash is
  not labelled `agent_crash` — test: `<name>`
- [ ] A 32,768-token truncation and its `400` gives a line with 32,768 —
  test: `<name>`

### R22-2. `waiting` stays `waiting` while the need still has its lite

- `ladder_inner` (`src/campaign.rs` ~:2112, in `ladder_inner` ~:2030) counts any failed record of a need as decided.
  So after 11 full fails, ticket 14 reads `skipped` for the whole 11-lite
  attempt. Since F2, that is the normal path.
- Change: a need is decided when it has a failed record **and** either
  has no lite or already has a lite record.
- Optional: a need carried as failed that the catch-up won't retry
  (`catch_up_targets`) is decided at phase start.

Acceptance:
- [ ] Full failed, lite pending: the dependent is `waiting` — test:
  `<name>`
- [ ] Full and lite failed: the dependent is `skipped` — test: `<name>`

### R22-5. Old graded crashes are relabelled on every read path

- F2's relabel of `fault` to `failed` for a graded crash sits inside
  `backfill_rounds` (`src/campaign.rs` ~:1591). The loop `continue`s for
  any stage that has recorded rounds, so it never reaches recent cells.
- `/api/campaigns` (the Board list) doesn't call the backfill at all.
- Live after deploy: the `.36` Haiku cells
  (`…_163524` t10, `…_184431` t11) still read `fault`.
- Change: apply the relabel independently of the rounds backfill, on
  every path that loads a rollup (the list, the detail, the portal
  export). The rule stays the same: the stage manifest says
  `agent_failed`, and the cell has no `harness_fault`.

Acceptance:
- [ ] A stage **with** recorded rounds and an `agent_failed` manifest
  reads `failed` — test: `<name>`
- [ ] `/api/campaigns` and the detail endpoint agree — smoke fixture or
  test: `<name>`
- [ ] Live check after deploy: `…_184431` t11 reads `failed` (the
  reviewer runs it)

### R23-8. Per-ticket cost shows the API bill

- The cell summary line (`src/main_campaign.rs` ~:1268,
  `s0 … PASS 1/1 ($0.1174, 49 turns)`) prints
  the effective cost (API plus the compute floor). Since round 23, the
  budget and the cap are API dollars. In the calibration cell, ticket 0
  shows $0.1174 against a $0.09 budget, which reads as an overrun.
- `StageRecord` keeps only `effective_cost_usd`, so the per-ticket API
  spend can't be read back from `campaign.json`.
- Change:
  - Add `api_cost_usd` to `StageRecord`.
  - Print API dollars in the summary and on the Board, with the effective
    cost as a secondary figure.

Acceptance:
- [ ] `StageRecord` has `api_cost_usd`, and the sum over stages equals
  `total_cost_usd` — test: `<name>`
- [ ] The summary line shows the API dollars — test: `<name>`

- Change: say "no entry in the price snapshot src/cost/model_prices.json
  (add the model's catalog id there)".

Acceptance:
