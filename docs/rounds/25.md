## Why

The round-22 review (`22.md`, Review) found three display defects in the
new F2 and F3 code. Neither changes points.

## Items

### R22-1. The crash label matches the real crash, not loose text

- `mark_agent_crash` (`src/campaign.rs` ~:1425) fires on `output: 65536`,
  `output limit` or `not valid JSON` anywhere in the console. Its message
  hard-codes "65,536".
- Failure: the agent crashes for another reason after an earlier tool-call
  validation error it recovered from. The stage is then mislabelled as an
  output-limit crash.
- Change:
  - Match the `[TOKENS]` line whose `output` equals that turn's maximum,
    followed by the provider `400` in the same session.
  - Put the real number in the line.

Acceptance:
- [x] A console with a recovered JSON error and a later unrelated crash is
  not labelled `agent_crash` — test:
  `campaign::tests::r22_1_a_recovered_json_error_is_not_an_agent_crash`
- [x] A 32,768-token truncation and its `400` gives a line with 32,768 —
  test:
  `campaign::tests::r22_1_a_32_768_token_truncation_reports_the_real_number`

### R22-2. `waiting` stays `waiting` while the need still has its lite

- `ladder_inner` (`src/campaign.rs` ~:2112, in `ladder_inner` ~:2030) counts any failed record of a need as decided.
  So after 11 full fails, ticket 14 reads `skipped` for the whole 11-lite
  attempt. Since F2, that is the normal path.
- Change: a need is decided when it has a failed record **and** either
  has no lite or already has a lite record.
- Optional: a need carried as failed that the catch-up won't retry
  (`catch_up_targets`) is decided at phase start.

Acceptance:
- [x] Full failed, lite pending: the dependent is `waiting` — test:
  `campaign::tests::r22_2_a_full_failure_waits_for_the_lite`
- [x] Full and lite failed: the dependent is `skipped` — test:
  `campaign::tests::r22_2_a_full_failure_waits_for_the_lite` (second half)

### R22-5. Old graded crashes are relabelled on every read path

- F2's relabel of `fault` to `failed` for a graded crash sits inside
  `backfill_rounds` (`src/campaign.rs` ~:1591). The loop `continue`s for
  any stage that has recorded rounds, so it never reaches recent cells.
- `/api/campaigns` (the Board list) doesn't call the backfill at all.
- Live after deploy: the `.36` Haiku cells
  (`…_163524` t10, `…_184431` t11) still read `fault`.
- Change: apply the relabel independently of the rounds backfill, on
  every path that loads a rollup (the list, the detail, the portal
  export). The rule stays the same: the stage manifest says
  `agent_failed`, and the cell has no `harness_fault`.

Acceptance:
- [x] A stage **with** recorded rounds and an `agent_failed` manifest
  reads `failed` — test:
  `campaign::tests::r22_5_a_stage_with_recorded_rounds_still_relabels`
- [x] `/api/campaigns` and the detail endpoint agree — test:
  `web::server::tests::r22_5_board_and_detail_agree_on_a_graded_crash_relabel`
- [ ] Live check after deploy: `…_184431` t11 reads `failed` (the
  reviewer runs it)

### R23-8. Per-ticket cost shows the API bill

- The cell summary line (`src/main_campaign.rs` ~:1268,
  `s0 … PASS 1/1 ($0.1174, 49 turns)`) prints
  the effective cost (API plus the compute floor). Since round 23, the
  budget and the cap are API dollars. In the calibration cell, ticket 0
  shows $0.1174 against a $0.09 budget, which reads as an overrun.
- `StageRecord` keeps only `effective_cost_usd`, so the per-ticket API
  spend can't be read back from `campaign.json`.
- Change:
  - Add `api_cost_usd` to `StageRecord`.
  - Print API dollars in the summary and on the Board, with the effective
    cost as a secondary figure.

Acceptance:
- [x] `StageRecord` has `api_cost_usd`, and the sum over stages equals
  `total_cost_usd` — test:
  `campaign::tests::r23_8_stage_api_cost_sums_to_total`
- [x] The summary line shows the API dollars — test:
  `main_campaign::tests::r23_8_summary_line_shows_api_dollars`

### R24-7. The refusal message names the real price source

- Since round 24, prices come only from the committed snapshot
  (`src/cost/model_prices.json`). The paid-launch refusal
  (`src/campaign.rs` ~:1861) still says "no list price in the OpenRouter
  catalog or offline table".
- Change: say "no entry in the price snapshot src/cost/model_prices.json
  (add the model's catalog id there)".

Acceptance:
- [ ] The refusal names `model_prices.json` — test: `<name>`

## Implementer notes

- R22-1: `mark_agent_crash` now splits the console at
  `[LIVE] Agent initialized`, takes the largest `[TOKENS]` output in each
  session, and labels the crash only when a provider `400` follows that
  turn in the same session. The line carries the measured count
  (`32,768`, `65,536`), not a constant. Tests:
  `r22_1_a_recovered_json_error_is_not_an_agent_crash`,
  `r22_1_a_32_768_token_truncation_reports_the_real_number`, and the
  existing `f2_mark_agent_crash_records_the_output_limit` with its 400.
- R22-2: `ladder_inner` decides a failed need only when it has no lite or
  already has a lite record; a failed full with a pending lite leaves the
  dependent `waiting`. `f3_phase_ladder_waits_for_a_pending_need` now
  covers the full-then-lite sequence; the dedicated test is
  `r22_2_a_full_failure_waits_for_the_lite`.
- R22-5: `relabel_graded_crashes` applies the manifest/`harness_fault`
  rule to every stage before the rounds backfill's `continue`. The detail
  endpoint calls it through `backfill_rounds`; the Board list calls it in
  `campaign_board_view` and writes the corrected rollup back; the portal
  export calls it on its parsed rollup. Tests:
  `r22_5_a_stage_with_recorded_rounds_still_relabels`,
  `r22_5_board_and_detail_agree_on_a_graded_crash_relabel`.
- R23-8: `StageRecord.api_cost_usd` is the provider bill and
  `effective_cost_usd` stays the compute-inclusive secondary figure.
  `stage_summary_line` prints `($0.1174 API, $0.1374 effective, N
  turns)`; the Board's ladder hover, ticket detail and ticket table show
  API first and fall back to effective for pre-field rows. The campaign
  sum test pins the stage API sum against `total_cost_usd`.
