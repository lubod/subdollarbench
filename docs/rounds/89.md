## Items

### F1. The torn tail never cuts into an older commit

The (c) step cuts `crash::torn_tail(&path, 256)` (`src/pipeline.rs:245`),
and `torn_tail` cuts `bytes.min(len / 2)` (`src/verifier/sql/crash.rs:477`),
whatever the victim commit wrote; `changed_file` computes `grew`
(`src/verifier/sql/crash.rs:413-414`) and drops it. A one-row INSERT
grows a statement log by ~40-60 bytes, so the 256-byte cut also tears
the record before it (the last 1000-row bulk INSERT), and a correct
checksummed log loses 1000 rows. The ticket's own prompt
(`campaigns/sdb-sql/stages/5_crash/prompt.md:20-25`) says the cut comes
from "the region your last commit grew" and only the newest statement
may be lost. In haiku's `.48` repair log the agent showed a 300-byte cut
gives exactly 99000/100000.

Fix: cut `min(256, grew, len / 2)` bytes from the file the victim grew;
when it grew nothing tearable, try another victim (the existing retry).

Acceptance:
- [x] `torn_tail`/the (c) step never cuts more than the victim commit
      grew — test: `r89_f1_cut_never_exceeds_the_commit`
- [x] A store whose log records are smaller than 256 bytes (a compact,
      checksummed, append-only statement log) passes (c) — test:
      `r89_f1_compact_log_store_passes_the_tear`
- [x] A store that loses an older committed record across the tear still
      fails (c) — test: `r89_f1_losing_an_older_record_still_fails`
- [x] Each seen failing
