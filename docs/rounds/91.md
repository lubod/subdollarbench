## Why

The `.50` bar (`sdb-gates/flake-13231b457717.txt`, 2026-11-18) takes
about 8 hours: one pass of its 30 proofs is about 24 minutes. Per proof
(seconds per run, from that record): the two stage-20 proofs 221 and
220 (each about 15 % of the bar, and **both** grade the whole ladder
0-20), `r45_f1_reference_scores_one` 364 (5 runs), the ticket-2-less
reference 79, the rest 1-68 (most about 26).

And the bar is not catching what costs money. It grades known-good
reference servers 20 times, so it measures **flakiness**, not
**correctness**: the coverage reading (round 88), the proxy buffering
(round 87), the torn tail and the ticket-2 syntax (round 89) all passed
every bar. Operator, 2026-11-18: "is there any possibility to make this
bar optimized and faster and effective?", then "91" (all four items,
including fewer passes for untouched proofs: a change to DECISIONS #26,
recorded as #37).

### B2. Twenty passes where the change is, five elsewhere

`bar_target` (`scripts/bar-proofs.sh:32-37`) gives every proof 20 runs
(5 for `r45_f1`). Make the target depend on what changed since the last
passing bar: a proof that `scripts/proof-map.txt` maps to a changed
grader path (or `core`, or a shared helper in `src/pipeline/tests.rs`,
as `scripts/proof-map.sh` already decides for `--ready`) keeps 20; every
other proof runs 5. The record states, per proof, its target and why
(the changed paths that selected it). With no previous passing bar, or
a change to a path every proof depends on (`src/pipeline.rs`'s grading
path, `src/grading.rs`, `src/verifier/sql/driver.rs`, the toolchain),
every proof gets 20, as today.

Acceptance:
- [ ] A change to `src/verifier/sql/crash.rs` only: the stage-5 proofs,
      the class proofs mapped to it and the core proofs run 20, the rest
      5 — test: `r91_b2_targets_follow_the_change`
- [ ] A change to `src/pipeline.rs` or `src/grading.rs`: every proof 20
      — same test
- [ ] No earlier passing bar: every proof 20 — same test
- [ ] The record names each proof's target and reason — check: a
      `--list` dry run in the notes
- [ ] Seen failing

Acceptance:
- [ ] Two parallel proofs never share a worker or port, and no timing

      `r91_b3_parallel_only_untimed`
- [ ] An unlisted proof runs alone — same test
- [ ] Seen failing

### B4. Proofs that catch a wrong grade, not just a flaky one

- **Negative proofs** (a broken fixture must FAIL the stage, with the
  expected reason), at least:
  - stage 5: a store that loses an older committed record across the
    torn tail;
  - stage 11: a store with no index (a full scan) fails the perf gate;
  - stage 6 or 12: a store that lets a dirty read or a lost update
    through;
  - stage 15: a test suite that stays green when the feature is reverted.
- **Real-workspace replay**: a small fixed set of real candidate
  workspaces from past runs (at least two: one haiku `.48` phase-4
  workspace and one deepseek workspace, copied without `target/`, logs
  or keys), each with its expected verdict per stage. A proof regrades
  them and fails when a verdict changes; a round that changes a verdict
  on purpose updates the expectation and says why in its notes.
- These run 3 times per bar (they are deterministic fixtures; their job
  is to catch a grader change, not flakiness).

Acceptance:
- [ ] Each negative proof fails its stage with the expected reason, and
      is seen failing when its check is weakened (for example the
      torn-tail check accepting any count) — tests:
      `r91_b4_neg_stage5_lost_older_record`,
      `r91_b4_neg_stage11_full_scan`, `r91_b4_neg_isolation`,
      `r91_b4_neg_stage15_insensitive_suite`
- [ ] The replay proof passes on today's grader and fails when a stage's
      verdict changes — test: `r91_b4_replay_real_workspaces`
- [ ] The fixtures hold no key, no prompt with secrets, no `target/` —
      check: the secret scans and a listing in the notes
- [ ] The new proofs are in `scripts/bar-proofs.sh` with target 3 and in
      `scripts/proof-map.txt` for the files they guard
