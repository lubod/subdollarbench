### F1. No two tests share a host port or a temp path

- **Ports:**
  - Give each test that starts containers its own worker number, or
    move the pair that meets on 15380. Either way, add a check.
  - The check is a unit test that lists every test's worker and task
    (one table in `src/pipeline.rs` tests, or wherever the workers are
    defined). For each one it computes every host port the test can
    bind:
    - the candidate's `worker_port(task base, w)`;
    - the references: ref-redis 6380, ref-http 8081, ref-sql 5481;

    run at the same time would bind the same port. Tests serialized by

    this check. They're 20000-59980, and the worker ports stay below
    20000; the check asserts that too.

  `:1550`) get distinct directory names. Grep for any other
  `temp_dir().join(format!(...process::id()))` name used by more than
  one test, and fix it the same way. The reviewer found only this pair.
  The `subdollar-ref-sql-src-<instance>` names are per instance, which is
  fine.

**Findings:**

- **R37-1 (blocker): the port check doesn't check ports.**
  - `r37_f1_worker_ports_do_not_collide` (`src/pipeline.rs:6432`) asserts
    two things:
    - the `let worker = N` IDs are unique;
    - `worker_port(6379, 90) != worker_port(5480, 70)`, two constants.
  - Neither one catches the bug F1 is about. Round 34's 15380 collision
    was between two distinct workers on two tasks: Redis 90's ref-redis
    (`6380 + 9000`) and SQL 99's candidate (`5480 + 9900`).
    - The check would pass if only that pair existed.
    - A new SQL test at worker 99 would pass it today. So would any SQL
      worker `w` next to a Redis worker `w - 9`, or an Http worker `w`
      next to a SQL worker `w + 26`.
  - It also misses the struct-literal form: `worker: 99,` in
    `test_pipeline_buffers_and_writes_console_log` (`src/pipeline.rs:8403`),
    the same ID as the proxy full ladder's.
  - **Fix, as F1 asks:** for each test, take its worker and task. Compute
    every host port it can bind:
    - the task's base;
    - the references: 6380, 8081, 5481;
    - the extra ports: 6395, 8090, 7001-7003;
    - SQL's +50 and +60..62;
    - the proxy pool 8101-8103.
    Then assert that no two tests share one, except two tests that both
    hold `SQL_PERF_LIVE`. The failure message names both tests and the
    port.
  - **Proof:** under Implementer notes, show that the check fails when
    the stage-6 proof is set back to worker 99 (with any other repeats
    removed).
- **R37-2 (blocker): R36-1 isn't met, and its test proves nothing.**

    `src/verifier/sql/scenarios.rs:90`), not to the run log or the stage
    outcome, as F5 asks. A cell's archive never sees it.
  - `r36_1_persistence_moves_off_a_bad_seed` XORs the constant twice,
    then calls `sentinel::build` directly. That is round 36's test again.
    It doesn't run `persistence` or the driver, and it checks nothing
    about where the seed ends up.
  - **Fix:** put the used seed in the stage outcome, for example a
    `sentinel_seed` next to `StageOutcome.seed`
    (`src/verifier/sql/driver.rs:341`), or in the run log through the
    pipeline's logger.
  - **Test:** run the persistence path (the driver, or `persistence`
    against the in-process reference server, as `ref_server.rs:1647`
    does) with a run seed that maps to a known bad seed. Check two
    things:
    - the result passes and the used seed is recorded;
    - the seed isn't in the candidate-visible failure text.
