## Why

Operator, 2026-11-19, asking to add `tencent/hy4-flash`: "I need to be
able to add models in future, why is it graded?"

- The price table is compiled into the binary
  (`include_str!("model_prices.json")`, `src/cost/calculator.rs:443`),
  so a new row needs a release rebuild.
- `src/cost` is a plumbing path (`scripts/graded-paths.txt:40`), so any
  row changes the full key: a new `$0` rehearsal, and a running grid
  refuses its next phase. Adding hy4-flash would block mimo's career
  although mimo's own row did not change.
- The protection itself is right: a model's price row decides its
  result (each ticket's share of the $0.99 and, since `.48`, its turn
  and time limits), so a wrong or changed row must not slip into a
  career. It just belongs to **that model**, not to every model.

## Items

### M1. The model registry is read at run time and is outside the global key

- The rows move from `src/cost/model_prices.json` to a registry the
  binary reads at run time (for example `models/registry.json`, one
  entry per model: id, base prompt/completion/cache prices, pinned
  provider, the price overrides that today live in
  `src/cost/calculator.rs`, an `added` date and a source note). Every
  existing row moves unchanged.
- The registry is outside the graded key (both keys) and outside the
  fingerprint; `scripts/graded-paths.txt` says so with a comment.
- The paid-launch refusals (`src/campaign.rs:2241-2254`) read the
  registry and name it in their messages.

Acceptance:

      compiled row, field by field — test: `r94_m1_registry_matches_the_snapshot`
- [ ] Adding a row for a new model changes neither key — test:
      `r94_m1_new_row_keeps_the_keys`
- [ ] A missing or unparsable registry refuses a paid launch with a
      clear message (never a silent default price) — test:
      `r94_m1_bad_registry_refuses`
- [ ] Each seen failing

### M2. Each model is protected by its own row's hash

- Every cell records the row it used and its hash (`price_row`,
  `price_row_sha`) in `campaign.json`, and the board shows the hash.
- A chained phase refuses when the model's row hash differs from its
  predecessor's (`validate_chain`, `src/campaign.rs:921`), so a row
  can't change mid-career.
- The model-check record stores the row hash it checked; the grid's
  preflight and `sql-cell.sh` refuse an official cell whose model's
  current row hash differs from the record's (the check must be rerun
  after a price change).

Acceptance:
- [ ] `campaign.json` carries the row and its hash — test:
      `r94_m2_cell_records_its_row`
- [ ] A changed row between phase 1 and phase 2 refuses phase 2 —
      test: `r94_m2_row_change_refuses_the_chain`
- [ ] A changed row after the model check refuses the grid — test:
      `r94_m2_row_change_needs_a_new_check`
- [ ] Each seen failing

### M3. `scripts/add-model.sh <openrouter id>`

- Fetches the model's endpoints from OpenRouter
  (`/api/v1/models/<id>/endpoints`), lists the providers, and with
  `--provider <tag>` (required when there is more than one) writes the
  registry row: the provider's **base** prices. When the endpoint shows
  a `discount`, the row stores the undiscounted base price and the
  script prints a warning that the real bill will be lower while the
  discount lasts (DECISIONS #32: scoring at base rates). It refuses an
  endpoint without tool-call support.
- `--dry-run` prints the row without writing it. It never prints the
  key. Then it tells the operator to run `scripts/model-check.sh` for
  the model.
- A self-test with a recorded endpoints fixture (no network).

Acceptance:
- [ ] A fixture with one provider and `discount: 0.5` writes the base
      price and warns — test: `r94_m3_add_model_base_price`
- [ ] Several providers without `--provider` refuse, listing them;
      no tool support refuses — same test
- [ ] Seen failing

### M4. The rules for adding a model

AGENTS.md ("Standing rules") gets a short "Adding a model" paragraph:
adding a model is `scripts/add-model.sh`, then the model check, then
the operator's word; no round. Changing an **existing** model's row is a
reviewed change (a round), because it changes that model's results; its
running careers refuse (M2). The reviewer commits AGENTS.md on merge
(the implementer proposes the text in its notes).

Acceptance:
- [ ] The proposed AGENTS.md text is in the notes
