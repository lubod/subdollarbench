## Why

The round-27 review (`27.md`, Review and Re-review) left five follow-ups.
They all affect whether the freeze's stamp and flake bar can be trusted,
so they land before the 20-pass flake bar runs:

- **R27-8:** the reference SQLite that grades every answer is
  `rusqlite` 0.32.1's bundled `libsqlite3-sys` 0.30.1, pinned only by
  `Cargo.lock`. Neither the stamp nor the flake key covers it.
- **R27-9:** `scripts/flake-bar.sh:14` copies `GRADED_PATHS` from
  `scripts/gate.sh:38`. Both lists also miss inputs that round 27 made
  graded: `build.rs`, `src/report/graded-files.txt`, `extensions/` (in
  the flake list only) and `Cargo.lock`.
- **R27-4:** the first failure stops a whole flake-bar chunk
  (`break 2`), and `--only` prints a summary for that one proof alone.
- **R27-5:** no test ties `build.rs`'s digest to the manifest:
  `r27_f1_compiled_in_files_hash_the_build` exercises the test helper
  `fingerprint_files`.
- **R27-7:** `CAP_PRICE_BASIS` (`src/report/rules.rs` ~:762) has no
  caller outside the tests, so no reader of results sees "at list
  price".

**Order:** any change to a graded path moves the flake key (round 27,
R27-3), so the reviewer's 20-pass flake bar runs **after** this round
merges. Round 29 is the freeze itself.

**Findings:**

- **R28-1 (blocker): the Board and the portal label every run with
  today's oracle and cap basis.**
  - Nothing records the SQLite version or the cap basis when a run is
    graded. The values are filled in at read time from the running
    binary:
    - `manifest_with_portal_flag` sets `sqlite_version` and
      `cap_price_basis` on every detail (`src/web/server.rs` ~:1306);
    - the Board header falls back to `window.__SDB_SQLITE__` and
      hard-codes "cap at list price (model_prices.json)" for every run
      (`src/web/index.html` ~:2865);
    - the portal appends the current `sqlite_version()` to each cell's
      rules column (`src/report/portal.rs` ~:1622).
  - So after a SQLite update every old run reads as graded by the new
    one. And runs from before `.39`, when the price snapshot wasn't the
    only price source (`24.md`), already read "cap at list price"
    today. That's the read-time relabel defect that R22-5 had to clean
    up.
  - Fix:
    - Record `sqlite_version` (and the cap basis, or let it follow from
      the rules version) in the campaign rollup and the run manifest
      when the run is graded.
    - Show the recorded value. A run without it shows "—" for SQLite,
      and no "list price" label when its rules are older than `.39`.
    - The server's own status (`/api/status`) can keep the current
      values; that one describes the binary, not a run.
  - Test: a fixture run recorded with SQLite `3.0.0` keeps showing
    `3.0.0` in the detail and the portal; a pre-`.39` run shows no
    list-price label.
- **R28-2 (next → round 29):** `graded_hash::collect_dir` ignores a
  missing directory. The round-27 `build.rs` panicked on one. A `dir`
  entry that is renamed or mistyped now hashes as nothing, which round
  27 ruled out for files ("A missing graded file must not hash as
  empty"). The build should fail on a missing `dir` entry.

**To fix:** R28-1 on `round28`, then gate and set `ready` again
(shortcut: `blockers`). The fix touches `src/campaign.rs` or the
