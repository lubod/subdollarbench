# Round 28: freeze hardening (oracle in the stamp, one path list, flake bar, cap shown)

Status: open
Opened: 2026-10-23, base: the commit tagged `round-28-open`
Branch: `round28`
Rules: `2026-10-19.40`, no bump (the stamp gains the oracle version, but
no grading changes)

## Why

The round-27 review (`27.md`, Review and Re-review) left five follow-ups.
They all affect whether the freeze's stamp and flake bar can be trusted,
so they land before the 20-pass flake bar runs:

- **R27-8:** the reference SQLite that grades every answer is
  `rusqlite` 0.32.1's bundled `libsqlite3-sys` 0.30.1, pinned only by
  `Cargo.lock`. Neither the stamp nor the flake key covers it.
- **R27-9:** `scripts/flake-bar.sh:14` copies `GRADED_PATHS` from
  `scripts/gate.sh:38`. Both lists also miss inputs that round 27 made
  graded: `build.rs`, `src/report/graded-files.txt`, `extensions/` (in
  the flake list only) and `Cargo.lock`.
- **R27-4:** the first failure stops a whole flake-bar chunk
  (`break 2`), and `--only` prints a summary for that one proof alone.
- **R27-5:** no test ties `build.rs`'s digest to the manifest:
  `r27_f1_compiled_in_files_hash_the_build` exercises the test helper
  `fingerprint_files`.
- **R27-7:** `CAP_PRICE_BASIS` (`src/report/rules.rs` ~:762) has no
  caller outside the tests, so no reader of results sees "at list
  price".

**Order:** any change to a graded path moves the flake key (round 27,
R27-3), so the reviewer's 20-pass flake bar runs **after** this round
merges. Round 29 is the freeze itself.

## Items

### F1. The oracle is in the stamp (R27-8)

- Hash the linked SQLite version (`rusqlite::version()`, the
  `sqlite3_libversion()` string) and the `rusqlite` and
  `libsqlite3-sys` versions from `Cargo.lock` into the stamp.
- Show the SQLite version next to the rules version wherever the stamp
  is shown (the Board's run header, `src/web/index.html` ~:2865, and the
  portal export).

Acceptance:
- [ ] Changing the recorded SQLite or crate version changes the stamp —
  test: `r28_f1_oracle_version_moves_the_stamp` (on a fixture, as the
  round-27 tests do).
- [ ] The engine's rules endpoint and a run's detail name the SQLite
  version — test: `r28_f1_detail_names_the_oracle_version`.

### F2. One graded-path list (R27-9)

- One file, for example `scripts/graded-paths.txt`, that both
  `gate.sh` (its `scope:` line) and `flake-bar.sh` (its key) read.
- It adds `build.rs`, `src/report/graded-files.txt`, `extensions/` and
  `Cargo.lock`.
- The AGENTS.md "Gates" paragraph that lists the paths points to the
  file instead of repeating it. The implementer proposes the wording in
  its notes, and the reviewer edits AGENTS.md after the merge.

Acceptance:
- [ ] Both scripts read the same file (no inline path list left) —
  check: `grep -n GRADED_PATHS= scripts/*.sh` is empty.
- [ ] A `Cargo.lock`-only commit moves the flake key and makes the
  gate's `scope:` line ask for the full gate — test: `flake-bar.sh
  --self-test`, extended.

### F3. Flake-bar ergonomics (R27-4)

- A failure is recorded, and the chunk goes on to the next proof, so a
  night still covers every proof. The script still exits non-zero.
- The summary always covers every proof, with `--only` too.

Acceptance:
- [ ] A fixture run with one failing proof records the remaining
  proofs, and its summary lists all of them — test: `--self-test`.
- [ ] `--only <t>` on a fixture where the other proofs have fewer than
  20 runs prints `IN PROGRESS`, not `PASS` — test: `--self-test`.

### F4. The build digest is tied to the manifest (R27-5)

- A test recomputes the compiled-in digest from the source tree, with
  the same algorithm and the same manifest, and asserts it equals
  `COMPILED_GRADED_DIGEST`. Move the shared hashing code to one place
  both `build.rs` and the test can use (for example `#[path]`-include
  one small module).

Acceptance:
- [ ] The test passes on a clean build and fails when the manifest and
  the build disagree — test: `r28_f4_build_digest_matches_the_tree`.

### F5. The cap basis is shown (R27-7)

- The Board's run header and the portal export show
  `CAP_PRICE_BASIS` (or a short form of it, such as "cap at list price
  (`model_prices.json`)"), next to the cap.

Acceptance:
- [ ] The engine serves the text, and the Board and portal render it —
  test: `r28_f5_cap_basis_is_rendered`.
