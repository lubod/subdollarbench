## Items

### F1. The result says the phase the rollup ran (R48-4)

`sql-cell.sh:121` writes `"phase": int(phase)` from the environment, so
`grid.sh:283` (`got_phase != phase`) compares the request with itself.

- The result takes `phase` and `chain_from` from the rollup
  (`CampaignRollup.phase`, `.chain_from`). With no rollup, `phase` is
  `null`.
- `grid.sh` stops the grid when the rollup's phase isn't the requested
  one, or its `chain_from` isn't the chain it passed.

Acceptance:
- [ ] A fake cell whose rollup says phase 2 for a phase-1 request, and
  one whose `chain_from` differs, each stop the grid with the reason in
  the ledger's `stop` column — check: `scripts/grid.sh --self-test`
  (new scenario), seen failing on master.

### F2. No phase starts next to a long test (R48-5)

The reviewer's old driver refused to start while a live proof, a flake
bar or another campaign ran (`pgrep`). `grid.sh`'s `preflight`
(`grid.sh:143`) checks the tree, the bar record and the worker's ports
only.

- `scripts/flake-bar.sh` and `scripts/gate.sh` in full mode hold
  `<git-common-dir>/sdb-gates/long-test.lock` (`flock -s`) for their
  whole run. `gate.sh --fast` and plain unit tests don't take it: they
  stay allowed while a cell runs (AGENTS.md, "While a cell runs").
- `preflight` refuses a phase while that lock is held
  (`flock -n -x` fails), says which, and writes STOP.

Acceptance:
- [ ] With the lock held by another process, `preflight` refuses and
  names it; with it free, it passes — check: `scripts/grid.sh
  --self-test` (new scenario, with the lock path injectable), seen
  failing on master.
- [ ] `flake-bar.sh --self-test` checks that a running bar holds the
  lock — check: its self-test.

### F4. The careers file is frozen once a grid starts (R48-7)

The ledger's first column is the career's line index
(`grid.sh`, `run_lane`), so a reordered or edited careers file gives a
ledger row to a different career.

- On the first start, `run_grid` copies the careers file next to the
  ledger (`<ledger>.careers`).
- A later start refuses, before any phase, if the careers file differs
  from that copy, and says how to start a new grid (a new ledger).

Acceptance:
- [ ] A restart with an edited careers file refuses and records no row;
  a restart with the same file resumes — check: `scripts/grid.sh
  --self-test` (new scenario), seen failing on master.

### F5. The flush counter reads one disk (R49-2)

`DeviceFlushCounter::flushes` (`perfscore.rs:873`) returns
the largest of every stat it found. On a device that spans two disks
(striped LVM, md RAID) the largest can come from a different disk at
each snapshot, so the window's difference means nothing.

- `for_dir` resolves the data dir's device to its whole disks (the
  partition's parent; a dm device's `slaves/`, recursively).
- One disk: read that disk's stat only. More than one: an error, so the
  perf block is a harness fault ("the data dir spans N disks"). The
  direct `st_dev` stat is used only when it has no disk under it.
- The sysfs root is injectable, so a test builds a fake tree.

Acceptance:
- [ ] A fake tree with a dm device over one partition reads that disk's
  field 16; one over two disks is an error — test:
  `r50_f5_flush_counter_one_disk`.
- [ ] On the bench host, `r49_f2_unsynced_candidate_floors_live` still
  passes — check: the gate.

## Changes after open

### F7. A floored workload says it is floored (operator 2026-10-30, "add to 50")

Added after the perf baseline (reviewer, 2026-10-30: `2cbea35`, data on
disk, the nine archived `.42` phase-end workspaces in
`sdb-archive/2026-10-28`, all five workloads). No `round50` commit
existed when it was added.

- **Wrong answer, raw ratio.** Three W3 blocks have `correct: false`,
  `ratio: 64.06` (haiku 033508), `73.20` (deepseek 221538) and `25.55`
  (muse 095127), and no `note`: the candidate answered in 0.04-0.10 ms
  with a wrong result. The score floors them already
  (`PerfScore::from_workloads`, `perfscore.rs:85`), but the stored block
  keeps the raw ratio (`result_with`, `perfscore.rs:402`, called from
  `run_latency` at `:692`), and a mismatch sets no note
  (`correct &= out.candidate_correct`, `:676`). Round 47's Perf hover
  would print "W3 64×" for a floored workload.
- **Slow, called wrong.** deepseek 010900's W1 is `correct: false` with
  the note `workload deadline after 467 queries` (`:598`; W5 the same at
  `:1292`): a correct but slow server. It floors either way, but the
  block can't tell a slow server from a wrong one.

The change:

- `result_with` (or its three callers, `:692`, `:1138`, `:1360`): when
  `correct` is false, `ratio` is `WRONG_FLOOR`, and the measured ratio
  goes under `numbers` as `raw_ratio` (absent when nothing was measured).
- The note always says why it floored: `the candidate answered wrong
  (query N)` for a mismatch, `too slow: the workload deadline passed
  after N queries` for a deadline, and the existing transport text
  otherwise. W4's "not durable" floor keeps its note.
- No score changes: `from_workloads` already floors on `correct`. No
  bump (`.44` unchanged); the fingerprint changes with the file, which
  this round already does.

Acceptance:
- [ ] A fake candidate that answers W3 fast and wrong stores
  `ratio == 0.1`, `numbers.raw_ratio > 1`, a note naming the wrong
  answer, and the same score as before the change — test:
  `r50_f7_wrong_workload_stores_the_floor`, seen failing on master.
- [ ] A fake candidate that answers right but past the deadline gets the
  "too slow" note, not a wrong-answer one — test: the same test, or
  `r50_f7_deadline_note_says_slow`.
