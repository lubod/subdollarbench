## Why

Round 45's W4 is "durable autocommit single-row `INSERT`" (`45.md`, F1;
the ticket-0 contract). Nothing checks that commits are durable:

- The reference commits with `synchronous=FULL`
  (`src/verifier/sql/ref_server.rs:651`, `:817`). W4 counts `OK 1`
  replies only (`src/verifier/sql/perfscore.rs`, `w4_side`).
- Ticket 5's crash test is a SIGKILL (`ref_server.rs:964`). Acked writes
  still in the page cache survive it, so the ladder doesn't check
  `fsync` either.
- The perf run's data dirs are in `std::env::temp_dir()`
  (`perfscore.rs:1234`). On the bench host that is tmpfs
  (`findmnt -T /tmp`: `tmpfs`), so `fsync` costs nothing on either side
  today. W4 measures in-memory inserts.

Once the data is on a disk, a server that skips `fsync` can reach W4's
100 clip: about ×2.5 on a five-workload score. Operator, 2026-10-29
(R45-4): **(a)**, a check before the v2 grid.

This round also takes round 45's two small findings on the perf block,
R45-3 and R45-6.

### F2. The flush check on W4's 1-client window

- During each side's 1-client W4 window, read the flush-request counter
  of the block device that holds the data dir:
  - `/sys/dev/block/<major>:<minor>/stat`, field 16 ("flush requests
    completed", Linux 5.5+), from the data dir's `st_dev`;
  - the bench host's rootfs is LVM on `nvme0n1` inside LXD, and
    `/sys/block/nvme0n1/stat` has 17 fields there. If the `st_dev`
    device doesn't report flushes, ask under Spec questions before
    walking `slaves/` to the disk.
- **Candidate:** fewer flushes than `0.9 ×` its acked 1-client commits
  in the window floors W4 (`correct: false`, note
  `not durable: <flushes> flushes for <commits> commits`).
- **Reference:** the same check runs on the reference's window. If the
  reference fails it, or the counter can't be read, the check can't be
  trusted on this host: a harness fault (no score).
- Other activity on the host (another lane, the agent's builds) only
  adds flushes, so a durable server is never floored by it. The 8-client
  run isn't checked (group commit is allowed).
- The counter source is injectable, so the unit tests can feed it.

Acceptance:
- [x] A candidate with fewer flushes than commits floors W4; the
  reference passing keeps the score — test:
  `r49_f2_flush_check_floors_unsynced` (fake engine, injected counter).
- [x] A reference that fails the check, or an unreadable counter, gives
  no score — test: `r49_f2_unreadable_counter_is_harness_fault`.
- [x] Live: the reference with `synchronous=OFF` as the candidate floors
  W4, while the reference against itself passes — test:
  `r49_f2_unsynced_candidate_floors_live` (under `SQL_PERF_LIVE`, so
  `scripts/live-proofs.sh` and the bar pick it up; the bar's self-test
  count goes from 27 to 28).

Findings:

- **R49-1 (blocker): `0bdc574` changes what a wrong answer is, outside
  the spec.**
  - `exec_busy` (`perfscore.rs:431`) retries a `busy` 4 times, then a
    `busy` insert is neither a commit nor wrong (`:950`, `:1202`), and a
    `busy` W5 read is skipped (`:1212`). In round 45 any answer other

  - Neither failed gate shows a `busy`: both failures were the tmpfs

    `busy`.

    ids `start_id..start_id + 5` (`:548`, called at `:973`, `:1242`).
    Those are the ids the 8 clients send together at the barrier. If
    one of them was a retried-out `busy`, the row was never written, so
    the sample fails: a correct server is floored, or the reference is
    a harness fault.
  - Fix: revert the scoring part of `0bdc574` (`exec_busy`, the two
    `busy` arms, the skipped read, and the sample back to the last ids
    of the window). Keep the clearer panic message in
    `r45_f5_perfscore_cli`. If the implementer has a run in which the
    reference answers `busy` on disk, put it under Spec questions

    entry, and a sample drawn from acknowledged ids only.
  - Acceptance: `git diff master...round49 -- src/verifier/sql/perfscore.rs`
    has no `busy`; the full gate passes.
- **R49-2 (next): the largest counter is only right on one disk.**
  `DeviceFlushCounter::flushes` (`perfscore.rs:888`) returns the
  largest of all the stats it found (`:892`). On a device that spans two
  disks (striped LVM, md RAID), the largest can come from a different
  disk at each snapshot, so the window's difference means nothing. It
  should sum the distinct whole disks, or call more than one a harness
  fault.
- **R49-3 (next): no unit test of a durable candidate over 2 rounds.**
  `StepFlush` (`perfscore.rs:1821`) is right for one window only: its
  second window reads 0 flushes. `r49_f2_flush_check_floors_unsynced`
  passes because the candidate's floor ends the rounds in round 1. The
  passing case is covered only by the live `r45_f5_perfscore_cli`. A
  fake that adds one flush per commit would test it without Docker.
- **Known limit (not a finding):** the counter is the whole disk's, so
  a server that runs `fsync` in a loop on another file passes the
  check. The spec accepted this ("other activity only adds flushes").
